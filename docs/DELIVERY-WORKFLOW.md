# Product delivery workflow

Status: proposed operating workflow based on the installed BMAD 6.12.0 catalog.
This document defines the process; it does not certify completion of its stages.

## Current position

The repository foundation is published. Baseline CI passed on commit 76b19c5dcd60e5ed47631c43a739738015afbe0d.
The product brief, PRD and architecture are conversation-derived drafts.
No Workstead application feature or runtime integration has been implemented.

## Responsibilities

- Astra performs analysis, drafting, implementation and review through available tools.
- BMAD provides the workflow, artifact expectations and readiness checks.
- GitHub stores the authoritative artifacts, issues, changes and validation results.
- GitHub Actions runs deterministic checks. It does not replace product decisions or provide permanent agent hosting.

## Sequence

1. `bmad-help` identifies state from installed configuration, catalog and actual artifact content.
2. `bmad-product-brief` may refine the existing brief without repeating resolved discovery.
3. `bmad-prd` reviews and develops the existing requirements. This is the next required planning step.
4. `bmad-ux` captures key screens and interaction decisions. Optional in BMAD, selected for this visual product.
5. `bmad-architecture` records the technical decisions; qualify critical runtime hypotheses before accepting them.
6. `bmad-create-epics-and-stories` derives scoped work and acceptance criteria from requirements and architecture.
7. `bmad-sprint-planning` checks implementation readiness (PASS/CONCERNS/FAIL) and creates the sprint status record.
8. `bmad-build` implements a scoped story, including its built-in review. Additional `bmad-code-review` is useful for critical changes.
9. Appropriate automated checks and human walkthroughs validate delivery; release to staging before production.

Use fresh focused contexts for major BMAD workflows. Each context reads repository artifacts.
Do not assume that installing skills means they are automatically active in every host session.
Do not mark a draft as approved merely because its file exists.

## Artifact locations and ownership

| Artifact | Authoritative location |
|---|---|
| Brief, PRD, UX and architecture | `_bmad-output/planning-artifacts/` |
| Epics and story acceptance criteria | BMAD planning/implementation outputs as generated by the installed workflow |
| Sprint and story progress | `_bmad-output/implementation-artifacts/` |
| Architecture decision records | `docs/architecture/decisions/` |
| Integration contracts | `docs/specs/` |
| Qualification scenarios and evidence summaries | `docs/validation/` |
| Research sources | `docs/research/` |
| Setup, deployment and recovery | `docs/operations/` and `docs/START-HERE.md` |
| Execution queue and discussion | GitHub Issues linking to the authoritative artifact |
| Code changes and review | Git branches and pull requests |
| Temporary logs/screenshots/build outputs | GitHub Actions artifacts with explicit retention |
| Durable large media | External artifact storage, selected later; version/digest references in Git |

Avoid independently maintained copies of the same specification. GitHub issue state tracks delivery; the linked specification defines acceptance.
No Jira for the initial development process. Jira may later be a connector supported by the Workstead product.

## Evidence and decisions

A requirement links to a story/issue, change, test evidence and released version.
The agent proposes defaults and records unresolved assumptions. Human decisions are requested for material product tradeoffs,
new paid services and production release scope, with concrete reviewable artifacts prepared first.
Only executed checks receive PASS. Baseline CI is not a product acceptance test.

## CI growth

Current: documentation structure and requirement-reference validation.
With implementation: lint/type checks, targeted unit tests, connector contracts and critical end-to-end paths.
With deployment: versioned build, staging smoke checks, migration/restore evidence and release/rollback records.
Configure provider secrets in the selected execution environment; do not commit them or assume setup-only secrets persist in an agent phase.
